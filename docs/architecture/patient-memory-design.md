# 患者长期记忆：当前实现与目标设计

设计参考：[医院 Agent 的长期记忆工程：从“记住用户说过什么”到 3 年可检索、可遗忘、可验证](https://blog.csdn.net/Anmory/article/details/170035015)。

## 当前代码什么时候写

当前只有两个写入时机，含义不同：

1. **长期记忆**：患者明确要求记住某件事时，主 Agent 调用 `save_patient_memory`，写入 `kind=long_term`。模型依据语义决定是否调用工具；现在没有单独的意图分类器，也没有对普通对话做回合结束抽取。
2. **会话归档**：每轮正常处理结束后，用户原话和助手回复分别写入 `kind=archive`。如果一轮进入 HITL，待确认摘要也会被归档。它用于后续会话语义查找，不等于从对话中提炼出来的长期事实。

每个新请求开始时，代码会按合成患者 ID 和当前用户消息做 BGE 向量检索，取 4 条结果放入主提示词；主 Agent 也有 `search_patient_history`，可在处理过程中再检索最多 5 条。检索查询当前没有过滤 `kind` 或有效状态，所以归档和长期记忆会一起参与排序。

## 博客方案的生命周期

博客把长期记忆拆成一组明确步骤。工程上建议按这个次序实现：

1. **识别写入意图**：用模型理解“以后别推荐含花生的东西”等表达，不靠固定关键词。用户明确要求保存时走最高优先级的显式写入；每轮结束后再做一次普通事实抽取，弥补 Agent 漏调工具的情况。
2. **抽取并留证据**：记忆写入患者/租户归属、类型、原文引用、重要度、置信度、来源会话和轮次、生效时间。普通抽取的内容必须能在原文中找到对应证据。
3. **处理更新与冲突**：旧事实保留并标为 `superseded`，记录 `validTo` 和替代它的新记忆；存在冲突但无法判断新旧时标为 `conflicted`，不擅自覆盖。用户明确纠正时以新事实为当前版本，同时保留审计记录。
4. **检索前先过滤**：先按患者隔离、类别、`active` 状态和时间范围筛选；询问过去某个时间点时再查历史版本。
5. **混合召回和精排**：关键词 BM25、向量相似度、图关系扩展分别召回，使用 RRF 合并后精排相关度、时效、重要度和访问情况。保护过敏、药物禁忌、剂量、编号、日期等精确事实。
6. **按上下文预算注入**：只把与当前问题相关的少量事实放进上下文，并携带来源和有效期；原始对话留在归档层，按需回读。
7. **遗忘与验证**：过期事实不再作为当前事实召回；低价值条目可以归档而非物理删除。通过跨会话回归问题检查抽取、更新、召回和拒答是否有效。

## 当前实现与目标的差距

目前存储表只有向量、文本、来源、患者 ID、类别和创建时间。还没有博客里的有效时间、冲突状态、重要度、置信度、引用证据、访问统计、BM25/图召回、重排、token 预算和容量治理。因此，不能把现有“向量归档”描述成已具备完整的三年长期记忆治理能力。

本次先把数据何时写入、当前实现与博客目标分开说明。补上自动抽取、版本化 schema 和多路召回会改变数据模型及写入流程，需作为独立实施项设计迁移与回填方案。
